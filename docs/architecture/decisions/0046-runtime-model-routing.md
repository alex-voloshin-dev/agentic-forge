# 0046 — Auto-route the validated model tier into runtime Task delegation

Status: Accepted — **implemented** (closes [ADR 0043](0043-multi-model-tiers.md) §5; see the
[Unreleased] CHANGELOG entry).

## Context

[ADR 0043](0043-multi-model-tiers.md) built the tier resolver (`models.model_for`) and wired it into
the **eval** runners, so a configured tier is gate-validated. But it explicitly **deferred** (§5)
threading the resolved tier into **live `Task` delegation**: when a skill body forks a subagent role
at runtime, the subagent's model is whatever its `agents/<role>.md` `model:` frontmatter says — today
`inherit` for all six roles. So a validated downgrade never actually reaches runtime; the eval path
and the runtime path are disconnected.

The runtime lever in Claude Code is the subagent's **`model` frontmatter field** (a documented
extension; accepts `inherit`, a model alias, or a model id) — CC reads it when delegating via `Task`.
The challenge ADR 0043 named: static frontmatter is, on its own, none of the three things tiering
must be — (a) opt-in / no-downgrade-by-default, (b) gate-validated, (c) centrally tunable.

## Decision

1. **A committed runtime tier policy — `models.VALIDATED_TIERS`.** Keyed by role, the gate-validated
   tier each agent runs at in live delegation. It **ships all-`default`** (no downgrade out of the
   box); a tier is promoted here only after it passes the eval gate at that tier. This is the single
   source of truth for runtime routing, and it ships *with* the agents, so a clean install is always
   self-consistent.

2. **A frontmatter resolver — `models.frontmatter_model(role)`.** The `model:` value for a role:
   `inherit` when the policy tier is `default` (follow the session model — safe, and respects a
   user's `/model`), else the concrete validated model id (`TIERS[tier]`). It uses the **same
   `TIERS`** the eval path uses, so for a **promoted** tier runtime pins exactly the model the gate
   validated; the `default` tier stays `inherit` (the session model) by design, not a pinned id.

3. **Tier-0 enforces frontmatter == policy.** `validate_agent` errors if an agent's `model:`
   frontmatter ≠ `frontmatter_model(role)` — so runtime routing can't silently drift from the
   validated policy (a hand-edit, or a policy change without a re-sync, fails the gate).

4. **A sync tool — `dev/sync_models.py`** (`--check` default / `--apply`). It regenerates the
   `model:` frontmatter from the policy: `--apply` rewrites the line; `--check` (like Tier-0) reports
   drift and exits non-zero. Promoting a tier is a gated sequence: validate the candidate via
   `settings.models` + the eval gate → add it to `VALIDATED_TIERS` → `sync_models.py --apply` →
   Tier-0 stays green → commit.

5. **`settings.models` stays the per-repo, eval-time override** (ADR 0043) used to *validate* a
   candidate tier before promotion; it does **not** feed the committed frontmatter or the Tier-0
   check — Tier-0 must be hermetic / deterministic across repos, and users must never edit
   installed-plugin frontmatter by hand.

## Alternatives considered

- **Feed `settings.models` (per-repo) into frontmatter / the Tier-0 check:** rejected — it makes
  Tier-0 non-deterministic across repos and pushes users to edit installed-plugin files. The
  committed policy is the runtime source of truth; `settings.models` is the eval-time lever.
- **Hand-edit frontmatter, no tool / no gate:** rejected — drift-prone and unenforced; the whole
  point is that runtime can't diverge from what was validated.
- **Pin opus explicitly as the default instead of `inherit`:** rejected — `inherit` is safer (it
  follows the session model and respects `/model`) and matches today's behaviour exactly.

## Consequences

- The validated tier now reaches **runtime `Task` delegation** via the agent `model` frontmatter,
  **enforced by Tier-0** and regenerated by a tool. **No behaviour change by default** (all-`default`
  → `inherit`, the current state). Closes ADR 0043 §5.
- Flipping a role to a cheaper tier is a gated one-liner (edit the policy → sync → gate), not a
  scattered hand-edit.
- Promotion still requires a **live** eval run at the candidate tier (manual, recorded — ADR 0043 /
  eval-runbook), so an un-validated downgrade still cannot ship.
